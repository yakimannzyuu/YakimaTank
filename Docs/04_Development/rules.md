# 開発の進め方（共通ルール）

## 0. この文書について

- **ルール版：2026.11.0**（変更点は [`rules-changelog.md`](rules-changelog.md)）
- 原本は [zeusisgood/agent-kickoff](https://github.com/zeusisgood/agent-kickoff)。この案件には原本から取り込み、**案件内の版を正とする**。取り込み元のコミットと、この案件で加えた改変は [`rules-changelog.md`](rules-changelog.md) の「この案件への取り込み記録」にある。
- 案件では、この文書と `Docs/05_Decisions/rules/` を直接直さない。変えるのは原本から取り込むときだけ（13 章）。案件固有の決まりは `AGENTS.md` か `Docs/05_Decisions/project/` に書く。
- コーディングエージェント（以下「エージェント」）が守るルール。特定のエージェントに依存しない。エージェントごとの設定は「付録 B」に置く。
- 本文は全案件に共通。案件の性質によって適用するものは「付録 A」、この案件（Unity・VRChat）固有のものは「付録 U」に置く。
- 各ルールの理由と採らなかった案は `Docs/05_Decisions/rules/` にある。ルールを変える提案をする前に読む。
- 原則：**質とスピードはトレードオフではない**。内部品質を下げると、結局は遅くなる。
- この文書は 300 行までを目安にする。超えそうなら、足す前に削れるものを探すか付録に移す。

## 1. 書き分けの原則

何をどこに書くかを、次のように分ける。

| 置き場所 | 書くこと | 具体的には |
|---|---|---|
| コード | How（どうやるか） | 読めば分かるコードにする。処理の説明コメントは書かない |
| テストコード | What（何を保証するか） | テスト名を日本語で書き、仕様として読めるようにする |
| コミットログ | Why（なぜ変えたか） | 件名は「何をしたか」、本文に理由 |
| コードコメント | Why not（なぜ他の方法にしなかったか） | 日本語で、採らなかった案とその理由 |
| ADR | 版をまたいで有効な決定と Why not | 技術・構成の決定、採らなかった案、未決事項（7 章） |

## 2. 進め方（相談 → 仕様書 → 実装）

- 要望に「相談」「ラフ」「整理」「計画」と付いていれば、実装しない。
  - 案を表に並べ、おすすめを 1 つ示し、「決めてほしいこと」を番号付きで聞く。
- 決まったら、先に仕様書 `Docs/02_Specifications/SPEC_YYYY-MM-DD_<内容>.md` を書く（雛形は `Docs/02_Specifications/_template.md`）。
  - 一覧 `Docs/02_Specifications/README.md` の表の一番上に 1 行足す。
  - **文書だけの変更**（README・Docs・コメントの修正）は、仕様書なしで進めてよい。それ以外（不具合の修正を含む）は仕様書を書く。
- 仕様書を承認したら、実装の前に作業の分解 `Docs/02_Specifications/TASKS_YYYY-MM-DD_<内容>.md` を書く（雛形は `Docs/02_Specifications/_tasks_template.md`。仕様書と同じ日付・内容名）。
  - 実装の順番をチェックリストにし、終えたら印を付けて同じブランチでコミットする。
  - セッションをまたぐときや中断から戻るときは、ここから再開する。
- **確認は仕様書の段階で行う**。下書きの仕様書は、ユーザーが「実装」と言うまで実装しない。
- 承認された仕様書にもとづく作業は、確認を待たずに実装から push・PR まで進める。
- セッションの最初の作業を始めるときは、原本のルール版を確かめる（13 章）。
- 作業を始めるときは、`Docs/05_Decisions/project/README.md` で「提案」状態の ADR を確かめる。決めるきっかけに当たっていれば、ユーザーに知らせる。
- ブランチを切る前に、開いている PR を確かめる。あれば番号・題名・ブランチを並べ、既存のブランチに積む・Merge を待つ・別のブランチで並行する のどれにするかを、ブランチ名の提案（3 章）と同じ返事で聞く。
  - 確かめられないとき（GitHub に入れないなど）は、一言添えて進める。人がいない実行（PR のコメントで呼ばれた Actions など）では確かめない。
- 仕組みに関わる変更の前に、関係する ADR（`Docs/05_Decisions/project/`・`Docs/05_Decisions/rules/`）を読む。
- **止まる条件**（当たったら push せずに止まって報告する）:
  - 承認済みの ADR に反する変更が必要
  - 仕様書にない、互換性を破る変更が必要
  - 仕様の意図が読み取れない
  - コードの誤りでビルドやテストが通らない（環境が原因の場合は 11 章）
- 仕様書に書かれていないことは、前の版と現行の実装のまま。
- 過去の仕様書が実装と違うと分かったら、本文は書き換えずに「（注: 実装では…）」を足す。
- ライセンスは仕様書の「0.」で決める。決まっていなければ聞く。
- 後回しにした作業は `Docs/04_Development/TODO.md` に残す。

## 3. ブランチ・コミット・PR

### ブランチ

- 長く残すブランチは `main` だけ。`main` への直接の push は禁止。
- 作業ごとに `main` から新しいブランチを切る。名前は `<エージェント名>/<内容が分かる英語>`（例：`claude/login-fix`）。
  - セッションに割り当てられた名前は使わない。
  - ブランチを切る前に名前を提案し、ユーザーの了承を得る。相談の「決めてほしいこと」に含め、相談を経ない依頼では最初の返事で聞く。依頼文で指定されていれば要らない。
  - 了承がないうちは、割り当ての名前で進めず、止まって聞く。
  - 取り込まれたブランチ名や、取り込み済みの PR を再利用しない。

### コミット

- 英語で、Git 本来の慣習に従う。
  - 件名は命令形の動詞から始める（`Add …`・`Fix …`・`Update …`・`Remove …`・`Refactor …`）。50 文字程度。
  - 理由（Why）は、空行の後の本文に書く。本文は 72 文字で折り返す。

### PR

- `main` に渡せる状態になったら（文書だけの変更でも）、エージェントが PR を作る。
- **PR を出す前に、書いた文脈から切り離したレビューを必ず通す**（8 章）。指摘は直してから出す。直さないものは PR 本文に理由を書く。
- PR 本文は「理由 / 変えたこと / 試してほしいこと」の 3 つ。
- 取り込みはユーザーが「Create a merge commit」で行う。ブランチの削除もユーザーが行う（エージェントは候補と削除コマンドを渡す）。
- **PR を出したあとは見張らない**（通知の購読や定期確認の予約をしない）。結果は、聞かれたときと次の作業を始めるときに確かめる。開いたままの PR があるときの扱いは 2 章。
- もう一度見てほしい PR は、ユーザーが PR のコメントでエージェントを呼ぶ（付録 B）。

## 4. バージョン

- 形式は SemVer（`x.y.z`）。版は `Assets/Yakimannzyuu/YakimaTank/package.json` の `version` に書く（ADR 0002）。
- `0.x` の間は開発中とし、正式公開で `1.0.0` にする。公開後は、互換を破る変更で major、機能の追加で minor、修正で patch を上げる。
- 互換を破るときは、`CHANGELOG.md` に何が変わり、利用者が何をすればよいかを書く。
- 版を書く所は `AGENTS.md` に一覧にして、すべて揃える。
- 文書だけの変更（コメントだけの修正を含む）では版を上げない。

## 5. リリースの手順

1. 仕様書を足し、`Docs/02_Specifications/README.md` の表に 1 行足す。
2. 版を書く所をすべて揃えて上げる。
3. パッケージの `CHANGELOG.md`（`Assets/Yakimannzyuu/YakimaTank/CHANGELOG.md`）の一番上に、新しい版の節を足す。見出しは `## [x.y.z] - YYYY-MM-DD`。
4. ルートの README の「最近の更新」（新しい 3 件）を直す。
5. 使い方が変わったら、利用者向けの文書（パッケージの `README.md` など）を直す。
6. 配布サイトの説明文が変わったら、PR 本文と報告に「説明文を貼り替えてください」と書き、新しい全文を添える。
7. コミットは次の順に積む。
   - `Add the spec for x.y.z`
   - 機能のコミット（1 つ以上）
   - `Release x.y.z: 〜`（版・README・CHANGELOG・Docs をまとめる）
8. 成果物をユーザーに渡し、PR のリンクと「試してほしいこと」を箇条書きで渡す。

## 6. コードとテスト

### 仕組みと図

- コードに触る前に、`Docs/03_Architecture/architecture.md` の関係する所を読む。仕組みを変えたら、同じ PR で直す。
- 図は Mermaid で書く。
  - 必須：**全体構成**（`flowchart`）と**主要な流れ**（`sequenceDiagram`）。`Docs/03_Architecture/architecture.md` に埋め込む。
  - 該当時のみ：状態遷移・データ構造・データの流れ。`Docs/03_Architecture/diagrams/` に 1 図 1 ファイルで置き、architecture.md から表でリンクする。
  - 1 つの図はノード 20 個まで。超えたら分割する。
  - 図と実装が食い違ったら、実装を正として図を直す。
- 共通の部品があるものはそれを使う。部品の一覧は architecture.md に置く。

### テスト

- 外部に依存しない純粋な計算は分けて、単体テストを書く。
- **TDD**：純粋な計算と不具合修正では、テストを先に書く（Red → Green → Refactor）。それ以外は推奨。
- 不具合は、再現するテストが失敗することを確かめてから直す。
- テスト名は日本語で、何を保証するか（What）を書く。言語の都合で関数名に使えない場合は、説明文字列に書く。

### 依存

- 新しいライブラリを足すときは、PR 本文に理由・代替案・ライセンスを書く。

## 7. 文書

### ADR（決定の記録）

- 置き場所は 2 つあり、番号は別々に振る。
  - `Docs/05_Decisions/project/`：この案件の決定。
  - `Docs/05_Decisions/rules/`：共通ルールの決定（agent-kickoff から取り込み）。**案件側では直さない**。変えたいときは agent-kickoff で直す。
- 書くのは、後から変えると手戻りが大きい技術・構成の決定（言語・DB・通信方式・保存形式など）。迷ったら書かない。
- 1 つの決定に 1 本。ファイル名は `NNNN-<英語の題名>.md`（4 桁の連番）。雛形は `Docs/05_Decisions/project/_template.md`。
- 一覧 `README.md` に、番号・題名・状態・1 行要約を足す。
- 状態は「提案 → 承認 → 置き換え」。
  - 決定を変えるときは、元の ADR を書き換えずに新しい ADR を作る。元の ADR は状態を「置き換え（NNNN へ）」にする。
  - 元の決定はそのままで補足だけ要るときは、本文末に「（注: …）」を足す。
- 未決事項：
  - 決めた事柄に付随する小さな未決は、その ADR の「未決事項」に、何を・なぜまだ・いつ決めるか（きっかけ）を書く。
  - それ自体が大きな未決の判断は、状態を「提案」にした ADR として作る。
  - `Docs/04_Development/TODO.md` には後回しの作業だけを置く。
- ADR はチャットで決めたときに、仕様書と一緒に作る。エージェントが実装中に新しい決定が必要だと気づいたら、「提案」の ADR を書いて止まる。

### そのほかの文書

- `AGENTS.md` には要点だけを書き、詳しいことは `Docs/` に分ける（目的別の表でリンクする）。エージェント固有の指示は、そのエージェントの入口ファイル（例：`CLAUDE.md`）に書く。
- README は入門だけにする（ダウンロード・対応環境・操作・最近の更新・文書へのリンク）。
- 利用者向けの文書には版の注記を書かない（更新履歴に書く）。
- 文書・PR 本文は日本語。ひらがなに開きすぎず、漢字を適度に使う。更新履歴は体言止めでよい。

## 8. 役割の分担

メインの作業（実装）は、文脈を共有したまま 1 つの会話で行う。次の 3 つは、メインの文脈から切り離して行う。エージェントにサブエージェントの仕組みがあれば使い、なければ同じ手順を自分で行う。

| 役割 | 内容 | 返すもの | 書き込み |
|---|---|---|---|
| 探索 | コードベースを広く探す | 結論と、根拠になったファイルパス・行番号 | しない |
| ログ要約 | テスト・ビルドを実行し、長いログを読む | 失敗箇所だけ（環境が原因のものは分けて書く） | しない |
| レビュー | PR 前に、main との差分をこのルールに照らして見る（観点の一覧は `.claude/agents/reviewer.md`） | 重大 / 要修正 / 提案 の指摘 | しない |

- 切り離した作業には、守らせたい規則（触らないディレクトリなど）を依頼の中で伝える。入口ファイルを読まない仕組みがあるため。
- エージェントごとの対応は付録 B。

## 9. （この案件では使わない）

- 原本の 9 章（devcontainer）は取り込んでいない。Unity と VRChat SDK はコンテナの中で動かせないため（ADR 0006）。章番号は原本と揃えるために残す。

## 10. 安全

- 秘密情報（トークン・鍵）は commit しない。`.env` は `.gitignore` に入れ、`.env.example` だけを置く。
- 次の操作はしない。エージェントに権限設定の仕組みがあれば、そこでも禁止する（付録 B）。
  - force push・`main` への push・履歴の書き換え
  - PR の Merge・リモートブランチの削除
  - `.env` の読み取り
  - リポジトリ外の削除
- 権限設定による禁止は、コマンドの書き方によってはすり抜けられる。**禁止を回避する書き方をしない**。

## 11. 環境

- 環境が原因でビルドできない（ネットワークの拒否・429 が続くなど）ときは、push と PR をしない。
  - コードの誤りとは分けて、拒否されたホストと直し方を報告する。
  - その間も、外部に依存しない部分のテストは流しておく。
- 一時的なエラー（429 など）は、間をあけて数回まで再実行する（例：30 秒ずつ 5 回まで）。

## 12. ユーザーとのやり取り

- 上限や制限は、黙って付けずにユーザーに聞く。
- エージェントが確かめられないこと（画面の描画・体感など）は、成果物で試してもらう。

## 13. 共通ルールとの行き来

案件と原本（agent-kickoff）の間で、ルールを両方向にやり取りする。

### 上り：案件で生まれたルールを原本に入れる

1. **気づく**：どの案件にも使えそうなルールが出てきたら、一言提案する（例：ユーザーが「これは毎回やりたい」と言った、同じ指摘を 2 回受けた）。強制はしない。
2. **控える**：`Docs/04_Development/TODO.md` の「原本へ提案」に、1 行の要約と相談した日を書く。
3. **相談する**：ルールの文案（どの章に入れるか）と、ADR の文案（理由・採らなかった案）を見せる。
4. **PR を作る**：**ユーザーから明示的に指示されたときだけ**、原本にブランチを切り、原本の `doc/rules.md`・`doc/rules-adr/`・`doc/rules-changelog.md` を直して PR を出す。作業の前に [`upstream-prompt.md`](upstream-prompt.md) の注意を読む。Merge はユーザーが行う。
5. **原本に PR を出せない環境では**：`upstream-prompt.md` の雛形を埋めたプロンプトを 1 本作って渡す。ユーザーがそれを PR を出せる環境に持ち出す。
6. **合流したら**：下りの手順でこの案件にも取り込み、`Docs/04_Development/TODO.md` の項目を消す。

### 下り：原本の更新を案件に取り込む

1. **確かめる**：セッションの最初の作業を始めるときに、原本の `doc/rules-changelog.md`（<https://raw.githubusercontent.com/zeusisgood/agent-kickoff/main/doc/rules-changelog.md>）を読み、一番上の版と、案件のルール版（0 章）を比べる。
   - 原本を読めないとき（通信の拒否など）は、止めずに「確かめられなかった」と一言添えて進める。
   - 人がいない実行（PR のコメントで呼ばれた Actions など）では確かめない。
2. **新しければ止めて相談する**：案件の版より新しい変更履歴の項目を、1 項目 1 行で並べ、関係する rules-adr の番号を添えて見せる。取り込むかを聞く。
3. **「後で」と言われたら**：`Docs/04_Development/TODO.md` の「原本から取り込む」に版を控え、元の作業に戻る。同じセッションでは再び聞かない。
4. **差分を確かめる**：`rules-changelog.md` の「この案件への取り込み記録」にある取り込み元のコミットから、原本の更新先のコミットまでの差分を読む。ファイル全体を原本で上書きしない。
5. **採用する変更だけを反映する**：案件内の通常の流れ（ブランチ → PR）で、採用する変更を手で反映する。次は維持する。
   - 取り込み記録で「取り込まない」とした記述とファイル（再び入れない）
   - SemVer（4 章、ADR 0002）・移動後の参照パス・付録 U・そのほか取り込み記録にある案件固有の改変
6. **確かめる**：反映した後、参照パスと相対リンクの先が存在すること、案件固有の改変が残っていることを確かめる。
7. **記録する**：取り込み記録に、更新先のコミット SHA・原本のルール版・採用した差分と見送った差分（理由つき）を足し、0 章のルール版を原本の版に合わせる。
8. 案件側で取り込みたくない変更が大きな決定に当たるなら、理由を `Docs/05_Decisions/project/` に ADR として残す。

雛形ファイルの差分をマージする仕組み（Copier など）は、今は使わない（rules-adr 0013 の未決事項）。

### 原本の版

- ルール版は原本（agent-kickoff）の版と同じで、形式は原本のまま `YYYY.M.N`。パッケージの版（4 章の SemVer）とは別に管理する。
- 原本を変えたら、原本の `doc/rules.md` 冒頭のルール版を上げ、原本の `doc/rules-changelog.md` の一番上に節を足す。

## 付録 A：該当時のみ

### A-1. 通信がある

- サーバーはクライアントから来た値を信じない（比べる・確かめるのに使うだけ）。
- 新しい機能は、相手のプロトコル版を確かめてから使う（古い相手とも動くように）。

### A-2. 多言語

- 画面の文字列は、すべての言語のファイルに足す。
- 言語のファイル同士でキーが揃っているかを、テストで確かめる。

### A-3. 設定ファイル

- 設定の項目名は変えない。移すときは、設定の版を上げて移行処理を書く。
- 設定を足したら、説明・`Docs/04_Development/config.md`・翻訳も一緒に足す。
- サーバーから受け取った値を、クライアントの設定ファイルに書き込まない。

### A-4. CI（GitHub Actions）

- CI の成功を Merge の必須条件にする。自分が作った PR の CI が赤くなったら、直して push する。
- 版の揃い・リリース手順の直し忘れを、テストで CI が赤くなるようにする。
- Dependabot の PR は、CI が緑ならユーザーが Merge してよい。赤ならエージェントが原因を調べる。

## 付録 U：Unity・VRChat（この案件で追加）

- アセットを足す・動かす・消すときは、`.meta` も一緒にコミットする。GUID を変えない（Unity の外でファイルを動かさない。`.meta` を作り直さない）。
- パッケージ内のパス（`Assets/Yakimannzyuu/YakimaTank/…`）をコードに直書きしない。VCC や git URL で入れると `Packages/com.yakimannzyuu.yakimatank/` に置かれ、書き込めなくなる。セットアップで作るアセットは、利用者の `Assets/` の下に出す。
- Runtime のコードでは、UdonSharp が対応しない C# の機能（自作のジェネリック型・自作の構造体・インターフェイス・`try`/`catch`・LINQ など）を使わない。迷ったら [UdonSharp の公式文書](https://udonsharp.docs.vrchat.com/) で確かめる。
- 同期は付録 A-1 の読み替えで考える。同期変数を書くのはオーナーだけ。オーナー以外から届いた値（ネットワークイベントの引数など）は信じず、確かめてから使う。
- エージェントは Unity と VRChat クライアントを動かせない。プレイ・見た目・VR / Desktop の操作・同期の確認は、仕様書の「5. ユーザーに確認してもらうこと」と PR の「試してほしいこと」に書く。
- テストは EditMode（`Tests/Editor/`）で書き、セットアップ処理と、UdonSharp に依存しない純粋な計算に絞る。テストはユーザーが Test Runner で実行する。
- `Assets/` の下で Git に入れるのは `Assets/Yakimannzyuu/YakimaTank/` だけ（ADR 0001）。`Docs/00_Memo/` は非公開のメモで、Git に入れない。その内容を公開するファイルに写すときは、ユーザーに確かめる。
